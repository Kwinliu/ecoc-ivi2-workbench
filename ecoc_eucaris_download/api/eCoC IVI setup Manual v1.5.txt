INTRODUCTION  
This manual outlines the structure, logic, and regulatory context of the Initial Vehicle Information 
(IVI) version 2.0 as implemented in the electronic Certificate of Conformity (eCoC). It is intended for 
everybody involved in the creation, validation, and exchange of vehicle data in XML format. 
 
It contains more detailed descriptions of the use of the eCoC and serves as a supplement to the IVI 
message book. Further documentation can be found on the eCoC website under menu item 
Documentation (https://ecoc.eucaris.net). 
 
IVI 2.0 introduces a standardized schema for encoding vehicle-specific data in compliance with EU 
framework directives 2018/858, 168/2013 and 167/2013. The manual provides detailed instructions 
on how to use fields related to the technical data such as: masses, axles, tyres, energy sources, and 
multistage vehicle configurations. It also addresses mandatory digital signing requirements effective 
from July 5th 2026. 
 
Information includes XML examples, regulatory references, and usage notes to support correct 
implementation and interoperability across systems. Special attention is given to cases such as hybrid 
configurations, optional indicators, energy sources, masses and multistage approvals. 
 
This document serves as a technical reference to ensure data consistency, regulatory compliance, 
and robust integration with national registration systems.

SIGNING AN ECOC  
With effect from: July 5th 2026: it’s mandatory to digitally sign all eCoC files. This will not only apply 
for the framework directive 2018/858 but also for the 168/2013 and 167/2013.

SUMMARY AND MINIMUM REQUIREMENTS:  
As a result of discussions within Ereg Topic Groep XII on CoC Data exchange and several 
manufacturers the minimum requirements for the signing certificate used for signing the eCoC, are 
as mentioned below. 
 
Manufacturers, in minimum, can use an advanced electronic seal to sign the eCoC messages which 
can be made with a non-qualified certificate. Article 36 of regulation 910/2014 states the 
requirements for such a seal. 
 
Manufacturers can (but are not required to) apply a qualified electronic seal which can be made 
with a qualified certificate. 
 
This seal must, at the latest, be applied as of July 5th 2026. 
 
Having a valid code signing certificate issued by qualified TSP and applying xmldsig will suffice to 
meet these requirements for submission of IVI messages. 
 
X-ADES can be applied, as best practice; however this is not mandatory.

USAGE INFORMATION  
The location of the vertical maximum static mass has been moved from the mechanical coupling 
table to its own table within the mass group. As a result, the maximum static vertical mass can be 
defined as follows: 
 
1. At vehicle level, when no coupling is installed, but towing maximum masses are available. For 
example, a passenger car that is delivered without a coupling device. 
2. At coupling level, by means of the MechnicalCouplingNumber as the identifier, which is also 
included in the mechanical coupling table. This allows the maximum static vertical mass to be 
linked to multiple attachment points on the vehicle. For example, when a vehicle has two 
coupling device options, such as a 50 mm ball coupling (75 kg) and a drawbar coupling (1,000 
kg). 
 
The S-value of the coupling device itself remains in the MechanicalCouplingTable.

MULTISTAGE VE HICLES  
REGULATION REFERENCE  
Multi-stage vehicle are vehicles that have been built and finished in more than one stage, normally 
by two or more different manufacturers. 
For example: Multistage vehicle chassis and cabin modifications involve an incomplete vehicle, like a 
chassis-cab, being completed by a second-stage manufacturer who adds specialized components to 
create a functional vehicle, such as a box truck or motor home. This two or more stage process 
involves different manufacturers adding parts to the vehicle's base to serve a specific purpose, like 
carrying cargo or functioning as a mobile workshop. 
 
Definitions (2018/858): 
‘multi-stage type-approval’ means the procedure whereby one or more approval authorities certify 
that depending on its state of completion, an incomplete or completed type of vehicle satisfies the 
relevant administrative provisions and technical requirements; 
 
‘base vehicle’ means any vehicle that is used at the initial stage of a multi-stage type-approval 
 
 ‘incomplete vehicle’ means any vehicle that must undergo at least one further stage of completion 
in order to meet the relevant technical requirements of this Regulation; 
 
 ‘completed vehicle’ means a vehicle resulting from the multistage type-approval that meets the 
relevant technical requirements of this Regulation; 
 
‘complete vehicle’ means a vehicle that does not need to be completed in order to meet the relevant 
technical requirements of this Regulation; 
 
With the implementation of EU 2018/858, the stage manufacturer is responsible for the data of the 
vehicle relating to the specific stage. Previously, it was the responsibility of the final stage 
manufacturer to consolidate all the data of the vehicle on the last stage CoC. 
 
This makes the process of processing the CoC’s for the registration purpose complex. This chapter 
describes how the multistage vehicles should be included within the IVI 2.0 messagestructure and 
how data could be processed. This will probably be different per Member State. 
 
Possible multiple stages in this process: 
 
From Status To Status To Status 
incomplete (I) completed (V)  
complete (C) completed (V)  
incomplete (I) incomplete (I) completed (V)

PROCESSING THE DATA  
Different methods can be used to process the data from different stage CoC’s. In principle, the data 
from the first stage must serve as a basis and differences with the subsequent stage must be 
processed.The processing of data for registration purposes can be different per Member State. 
 
Points of attention here are: 
Data which is part of a table (for example AxleTable) will have to be repeated in the second stage 
eCoC. If you have a first stage vehicle with three axles and in the second stage CoC there’s only one 
Axle stated, combining the two CoC’s could mean removing two axles or adding one. This is why the 
entire set must be included in the case of automated processing. 
 
Single fields at Group level not within a table 
For processing to a vehicle eCoC, the different eCoC’s can be superimposed on each other based on 
the order in ManufacturerStageNumber. By following this order, the data from the first eCoC is 
overwritten with the data from the subsequent eCoC. The issue with this processing is that single 
fields (e.g. ClassHybridVehicle) that were named in the first stage and have no value in the 
subsequent stage, remain because they are not overwritten with a new value and it is not clear 
whether they should be deleted.

HYBRID VEHICLES ( NOVC -HEV ) 
REGULATION REFERENCE  
UN Regulation No 177 - Uniform provisions concerning the determination of system power of hybrid 
electric vehicles and of pure electric vehicles having more than one electric machine for propulsion 
[2025/1910] 
3.3.13. "Not off-vehicle charging hybrid electric vehicle" (NOVC-HEV) means a hybrid electric vehicle 
that cannot be charged from an external source. 
3.3.14. "Hybrid vehicle" means a vehicle equipped with a powertrain containing at least two different 
categories of propulsion energy converters and at least two different categories of propulsion energy 
storage systems.  
3.3.15. "Hybrid electric vehicle" means a hybrid vehicle equipped with a powertrain containing at 
least one electric motor or electric motor-generator and at least one internal combustion engine as 
propulsion energy converter.  
USAGE INFORMATION  
In case of an NOVC-HEV (ClassHybridVehicle) vehicle, several energy sources must be included in the 
eCoC, including EnergySource: Electricity (95). Also the engine code for the electric engine has to be 
mentioned. If this engine does not have it’s own specifications, the manufacturer of the engine and 
the engine code must be repeated, working principle must be set to electricity. 
The fields which are relevant for the specified energy source have to be mentioned within that 
energysource group. For instance “MaximumNetPowerCombustion” only for EnergySource: Petrol 
(10), and “MaximumNetPowerElectric”only for EnergySource: Electricity (95). Also see chapter: 
EMISSION/SOUND/POWER AND CONSUMPTION FOR DIFFERENT VEHICLE TYPES.

REGULATION REFERENCE  
UN Regulation No 177 - Uniform provisions concerning the determination of system power of hybrid 
electric vehicles and of pure electric vehicles having more than one electric machine for propulsion 
[2025/1910] 
3.3.16. "Pure electric vehicle" (PEV) means a vehicle equipped with a powertrain containing 
exclusively electric machines as propulsion energy converters and exclusively rechargeable electric

USAGE INFORMATION  
In case of a pure electric vehicle (PureElectricVehicleIndicator = Y) the fields relevant for the electric 
engine and energysource have to be available in the eCoC. In case of several electric engines, the 
data for each engine must be added. If these engines do not have their own specifications, the 
manufacturer, engine code and working principle must be repeated. In case of a fully electric vehicle, 
the data specified for the energy source of the first engine must be repeated for the next engine(s), 
deviating values must be adjusted. Also see chapter: EMISSION/SOUND/POWER AND CONSUMPTION 
FOR DIFFERENT VEHICLE TYPES. 
 
Note: A different approach has been chosen for fully electric vehicles because it’s not clear how to 
enter the data for the different engines and energy sources. The data that applies to the engines 
sometimes apply to that specific engine or could be applicable for the vehicle as a whole. It has been 
discussed to have an option available to add energy source information on different levels in the 
message. This was not chosen because it would make the processing of the data too complex and 
difficult to check against the type approval. Therefore, the data must be repeated for this type of 
vehicle. Energy source electricity must be provided per engine, so the values must be repeated (if the 
same) for each engine because vehicle-level registration is not supported. This must be taken into 
account when processing to the registration processes.

USAGE INFORMATION  
The first version with the data of the vehicle must always contain the value "1" (mandatory). Only in 
the event of a correction of the data of the vehicle when, for example, the wheelbase is given a 
different value because it was incorrectly supplied in version “1”, the version must be increased to 
"2" etc. The value does not change if, for example, a delivery did not go well due to technical issues. 
Also for a corrected version the IvIReferenceId has to have a different value, same as 
IviVersionDateTime. 
EMISSION/SOUND/POWER AND CONSUMPTION FOR DIFFERENT VEHICLE TYPES  
HOW TO SET UP IN IVI  
For all vehicles M,N,L,T,C an EnergyConvertorCodeMarkedOnEnergyConvertor must be present. For 
hybrid vehicles, the electric engine may have its own code, then this must be entered. If this is not 
the case, the EnergyConvertorCodeMarkedOnEnergyConvertor of the combustion engine must be 
repeated. 
 
As a general rule always state the fields which are specified for the EnergySource. For instance 
MaximumNetPowerCombustion only for the fossile fuels, and MaximumNetPowerElectric only for 
electricity. See for specific rules the chapters for different vehicle types in this manual. 
 
The Excel “VehicleTypes-Power-Sound-Consumption” indicates which fields are relevant for different 
vehicle types. To be found in the eCoC manual folder.
